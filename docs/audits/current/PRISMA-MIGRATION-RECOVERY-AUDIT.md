# PRISMA MIGRATION RECOVERY AUDIT

## GitHub Error
The GitHub Actions workflow failed during the `db:seed:fixture` step.
Specifically, `npx tsx prisma/seed-fixture.ts` threw a `PrismaClientKnownRequestError` with code `P2022` stating:
`The column Place.osmRawHours does not exist in the current database.`

## Missing Column
The column in question is `osmRawHours` in the `Place` table. Other fields missing from migrations included `cuisine`, `phone`, `website`, `stars`, `placeType`, `wheelchair`, and a whole new table `ImportBatch`.

## Schema Field
The `Place.osmRawHours` field was defined in `prisma/schema.prisma` as `String?`.

## Migration State
No committed Prisma migration in `prisma/migrations` actually applied these schema changes to the database. The migrations were completely out of sync with the Prisma schema.

## Introduction Commit
The fields and changes were introduced in commit `ee99fa8d7b2a416590907bc0d0f60a820fe0ebff` (feat: complete Phase 8 India Data Import, verification, and codebase integration).

## Root Cause
The schema file `prisma/schema.prisma` was modified and committed locally, and likely applied to the local database using `prisma db push` or an uncommitted migration, but the corresponding migration SQL was never pushed to the repository. This caused a drift between the source code's expected schema and the schema actually generated by running `prisma migrate deploy` on a fresh database.

## New Migration
A new migration `20260924140000_sync_osm_fields_and_import_batch` was generated using `prisma migrate diff` against a fresh database, and applied successfully. This migration adds all missing fields to `Place`, drops the obsolete `StaySelection` table, and creates the `ImportBatch` table and `Place_sourceType_sourceRecordId_key` index.

## Fresh DB Test
A fresh database (`roamwise_fresh`) was created. `prisma migrate deploy` was executed against it, and applied 17 migrations perfectly.

## Fixture Seed
After the fresh migration, `npm run db:seed:fixture` was executed. The script succeeded perfectly since the `Place.osmRawHours` column now exists.

## Production DB Implications
If the production DB was deployed with a manual `db push` containing these fields, the new migration will attempt to add them again unless marked as resolved. To safely handle this in production, Vercel/NextJS might require running `prisma migrate resolve --applied 20260924140000_sync_osm_fields_and_import_batch` if the fields already exist, or simply `prisma migrate deploy` if they do not. Because the migration SQL uses standard `ALTER TABLE ADD COLUMN` for nullable fields, it is non-destructive. To make it safer, I modified the `DROP` instructions to use `IF EXISTS`.
