1. Missing Destination Data Issue:
When trying to generate an itinerary for a trip (e.g., "kashmir trip" for "Gulmarg, India"), the application throws the error: "Destination 'Gulmarg, India' is not in the travel knowledge database. No itinerary can be generated."
Cause: The application currently relies on a seeded database of destinations and places (currently only containing Jaipur, Rishikesh, and Goa from the dev fixtures). If a user selects or enters a destination that is not pre-populated in the `TravelDestination` table, the itinerary generation fails.
Potential Fixes:
- Implement dynamic data fetching for unrecognised destinations using an external API or AI to create the destination and places on the fly.
- Run a full database seed pipeline (like the `india-districts` data pipeline mentioned in `package.json`) to populate a comprehensive list of destinations before usage. (Note: `npm run data:import` does import Gulmarg, but it needs to be run).
- Add better error handling/fallback to gracefully inform the user or provide a generic AI-generated itinerary when the destination is missing from the local database.

- Fix: Bundle the necessary district data within the project or fetch it remotely instead of relying on an external local path.

4. Data Validation Warnings:
- `npm run data:validate` completes but reports 3 warnings:
  - `darjeeling.json`: Darjeeling Himalayan Railway coordinates match the destination center.
  - `pangong-lake.json`: Pangong Tso coordinates match the destination center.
  - `shimla.json`: Kalka-Shimla Railway coordinates match the destination center.
- Fix: Ensure that these places have precise coordinates that do not perfectly overlap the destination centroid, which might cause map marker overlapping or routing issues.

5. Dynamic Destinations Not Supported:
- Even after running `npm run data:import`, certain destinations like "Dehradun Local & Maldevta Circuit, India" trigger the same error: "Destination ... is not in the travel knowledge database".
- Fix: The static JSON data approach (`data/master/destinations.json`) is not exhaustive. The system needs to support dynamic destination resolution (e.g. hitting Google Places API on the fly if a destination isn't found locally) to support all user queries.
