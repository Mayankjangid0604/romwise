ISSUE-001
ID:          ISSUE-001
Title:       Accommodation model duplication — StaySelection vs TripAccommodation
Category:    Architecture / Database
Priority:    Medium
Status:      Open — intentionally documented, NOT yet migrated

Description:
  Two overlapping accommodation models exist in prisma/schema.prisma.

  StaySelection (legacy / simpler):
    Fields: hotelName, costPerNightInr, totalCostInr, nights, lat, lng
    Relation: Trip @unique (max 1 per trip)
    Usage: src/app/actions/stay.ts, stay/page.tsx, budget/page.tsx
    DB records: 1 row (LIVE — cannot be dropped without data migration)

  TripAccommodation (newer / richer):
    Fields: name, location, latitude, longitude, checkInDate, checkOutDate,
            checkInTime, checkOutTime, bookingReference, notes
    Relation: Trip[] (multiple per trip)
    Usage: src/app/api/trips/[id]/stay/route.ts, trips/[id]/page.tsx
    DB records: 0 rows (Foundation)

  Decision: TripAccommodation is the canonical long-term model. StaySelection
  remains live because it has 1 DB record and the stay UI references it.
  A migration is required before removing StaySelection.

Expected: Single canonical accommodation model (TripAccommodation) across all code.
Current:  Both models coexist; StaySelection drives stay/budget UI, TripAccommodation drives API.

Files:
  prisma/schema.prisma (StaySelection line 229, TripAccommodation line 426)
  src/app/actions/stay.ts
  src/app/trips/[id]/stay/page.tsx
  src/app/trips/[id]/budget/page.tsx
  src/app/api/trips/[id]/stay/route.ts
  src/app/trips/[id]/page.tsx
  src/lib/trip-validation.ts

Acceptance Criteria:
  1. Prisma migration maps StaySelection data to TripAccommodation
  2. All UI/API references updated to TripAccommodation
  3. StaySelection removed from schema
  4. stay.test.ts updated
  5. npm run build succeeds, all tests pass
  6. StaySelection has 0 DB records after migration
